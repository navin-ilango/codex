# IAM

`IAM Policies`
1. A set of statements to grant or deny permissions to AWS Resources.
2. Identity Policies are attached to IAM Identities.
3. Multiple Identity policies can be attachd to an IAM Identity and each policu can have one or more statements.
4. `Policy Order of Execution` - Explicit DENY -> Explicit ALLOW -> Default DENY (Implicit)

IAM Policy Types
1. Inline Policy - Attached to IAM Identities, Used for special or exceptional allow or deny.
2. Managed Policy - Reusable and Low management overhead.

Managed Policy Types
1. AWS Managed
2. Customer Manages

`IAM Users`
1. IAM Users are an Identity used for anything requiring long-term aws access. Ex: Humans, Applications & Service Accounts.
2. IAM Users are authenticated using username/password or access keys.
3. Amazon Resource Name (ARN) - Uniquely Identify resources within an aws account. Format: `arn:partition:service:account-id:resoource-id`
4. 5000 IAM Users per Account
5. IAM User can be a member of 10 groups. This has system design impacts for Large Orgs or Org Merges (IAM Roles and Identity Federation can fix this)

`IAM Groups`
1. IAM Groups are container for users.
2. Cannot login using IAM Groups
3. IAM User can be a member of multiple Groups.
4. Groups can have both InLine Policy and Managed Policy attached.
5. No Nesting - Cannot have a group within another group.
6. By default, 300 Groups per AWS Account, this is a soft limit and can be increased.
7. Groups are not a true Identity. They cannot be references as a Principal in a Policy.

`IAM Roles`
1. IAM Roles are best suitable when multiple users or principals requires access to resources in an AWS Account.
2. IAM Roles are assumed and you become that role for some time - That is you borrow the permissions for a short period of time.
3. IAM Roles can bave both Inline and Managed policies attached to it.
4. IAM Roles has 2 types of policy attached to it - Trust Policy & Permissions Policty.
5. `Trust Policy` define which identities are allowed to assume this IAM Role. These identities that are allowed to assume an IAM Role can be of the same aws account as the IAM Role or another aws account.
6. When an IAM User assumes an IAM Role, a Temporary Security Credential is generated and using this short time access credentials, the IAM User can now access the resources permitted by the permissions policy attached to the IAM Role. The temporary credentials are generated by an aws service called `STS`.

When to use IAM Roles?
1. AWS Lamnda - This is commonly called as Lambda Execution Role. This role has a trust policy that allows AWS Lambda to assume this Role whenever a function is invoked.
2. Break Glass -  IAM Roles can be used when you want to allow User X to temporarily get access to a specific resource.
3. AWS in a typical Corporate Environment - Single Sign On (SSO) - External accounts can't be directly used in AWS. Instead these accounts must assume an IAM Role to access resources in as AWS Account. We must use SSO if an org has more than 5000 accounts, since there is a hard limit that as aws account can have only upto 5000 IAM users. With `SSO & Web Identity Federation` - No aws creds are stored in a app or device, it uses existing customer logins and scales up to millions of accounts.
4. Cross Account Access - Allows users of account A to assume a roles in account B to get access to the resources in account B.

`Service Linked Roles`
1. IAM Role linked to a specific AWS Service.
2. It is predefined by a service providing permissions that a service need to interact with other AWS Services.

`Pass Role` - Role seperation can be implemented in an aws account using the `iam:passrole` action. This now allows user A to configure a service A with already existing IAM Roles and he just needs the passrole permissions on that role.
