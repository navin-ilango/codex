# Simple Storage Service (S3)

`S3 Security`
1. S3 is private by default - Only the Identity that has any access to the bucket or the root user or the Identity which created the bucket has access to the bucket.
2. Anyone other that the root user and the identity which create the bucket can be granted access using - Identity Policy or Resource Policy (aka. bucket policy)

`Bucket Policy`
1. It is like an Identity Policy, but attached to a bucket.
2. With identity policy we control what that identiy can access and with resource policy we control who can access that resource.
3. You can only attach Identiry policy to the Identities in your own account. In other words, with identity policy there is no way of giving an Identity in another account access to your account. But, Bucket Policies ALLOW/DENY access to Identities in the same or different accounts and aleo ALLOW/DENY anonymoous Principals.
4. Keep in mind that Identity Policies has to be attached to a valid aws identity. That is why a Resource policy can be used to open up a bucket to the world.
5. Bucket policy has an explicit `principal` compoient. `principal: *` - grants access to the world. That is identies in your account, partner account and anonymous can access the bucket.
6. There can only be one bucket policy atached to a bucket but the policy can have multiple statements.

`S3 Static Website Hosting`
1. Alloes access to objects in a bucket using HTTP.
2. When you configure a bucket for statis website hosting, you must set the index.html and error.html documents. The index.html is the entry point to the website and error.html will be served when error occurs.
3. When you enable static website hosting, AWS S3 creates a `website endpoint` based on the bucket name and region. The website endpoint is HTTP bu default.
4. If you want a custom domain for your website, you can use R53 but the DNS record name must be same as your bucket name. Fact: Bucket name matters. 
5. Usacases - Offloading, Out of Band Pages.

`S3 Pricing` - AWS S3 charges for Storage per GB, Data Transfer (Data In is always free) and Requests and Data Retrievals.

`Object Versioning`
1. Object versioning by default is disables but once enabled you cannot disable it again. However you can suspend versioning which can be re-enabled later.
2. Versioning lets you store multiple versions of objects within a bnucket. Operations which would modify the objects generate a new version.
3. S3 Object with versioning enabled has a KEY (Object Name) and ID (Version ID).
4. At any given point of time, if you access a versioning enabled s3 objects, you will always get the latest or current version of the object.
5. To access a specific version of an object, you must specify both the key and id as part of the GET request.
6. Space is consumed by all versions
7. Enabling S3 Object versioning makes the delete process complicated. When you delete an object, S3 adds a `Delete Marker` which makes the object and all its version hidden and you can recover those objects by deleting the Delete Marker but you can actually delete an object by version by specifying the exact version of that object and if the object you are deleting happens to be the current version then the previous version of that object becomes the current version.

`MFA Delete`
1. MFA delete can be enabled as part of the versioning configuration.
2. MFA is required for operations like changing the bucket versioning state and deletiong versions.
3. Serial Number (MFA) + the MFA Code is passed with the API Calls.

`S3 Performance Optimization`

1. `Single PUT Upload` - Single data stream to S3. If the stream fails then the entire upload fails and requires a re-upload. Speed and reliability is low because of the limited single stream. Allow upload up to 5 GB Only.
2. `Multi Part Upload` - Data is broken into multiple parts. Min data size for multipart upload is 100 MB. An upload can be split into a max of 1000 parts and each part can be of size 5 MB to 5 GB. Each individual part can fail and be re-uploaded, So it is more reliable.

`S3 Accelerated Transfer`

Using the public internet for getting data from a source to destination in a multi region or global architecture is not advisable because of the relatively indirect routing that the data takes to reach its destination and transfers take time because of the multiple hops and we have no control of this behaviour because the routers and ISP are picking up this path which they think is good.
With S3 Accelerated Transfer enabled, the data get transfered through the edge locations and dedicated aws global network which connect various regions with guaranteed speed.

Limitations to enable s3 accelerated transfer
1. Name of the bucket must be DNS coompliant.
2. Bucket name must not contain dots.
3. It might take up to 20 mins before the data transfer speed to the bucket increases.
4. Need to use the accelerated endpoint.

`Key Management Service - KMS`
1. Regional and Public Service
2. Create, Store and Manage Keys
3. Symmetric and Asymmetric Keys
4. Cryptographic operations - Encryption & Decryption.
5. Key never leaves KMS and offers FIPS 140-2 (L2) compliance.
6. In AWS KMS, the Keys are logical. It has an ID, Date, Policy, State and it is backed by the Physical Key.
7. Physical Key in KMS Key can be generated or imported.
8. KMS Keys can be used for up to 4 KB of data.
9. Data Encryption Keys: Generate Data Key -> Stores Encrypted Key with Data.
10. KMS Keys are isolated to a region and optionally multi region keys are available.
11. Keys are either AWS Owned or Customer Owned.
12. Two types of customer owned keys - aws managed keys, customer managed keys.
13. Customer managed keys are configurable. That is you can update the policy to allow cross account access but aws managed keys are not customisable this way.
14. Both AWS and Customer Managed Keys support Key Rotation.
15. KMS Keys has its backing key and all its previous backing keys. So a data encrypted using an older backing key post key rotation can also be decrypted.
16. KMS Keys can have aliases and these aliases are regional as well.
17. `KMS Key Policies` are Resource Type Policy and every key has one.
18. Key Policy + IAM Policy is required to access a Key.

`S3 Encryption`

1. This is about encrypting the s3 objects and not the bucket itself. S3 objects are encrypted in transit by default
2. Types of Encryption at Rest: Client Side Encryption and Server Side Envryption.

Client Side Encryption:
1. Client encrypted the data and then stored in S3.
2. Client is responsible for the Keys, Encryption Process and Tools.
3. S3 object is encrypted at any point in time.

Server Side Encruption:
1. S3 takes care of the process required to encrypt data on the server side before storing it.

3 Types of SSE:
1. SSE - C (Customer Provided Keys) - Customer manages the keys. S3 manages the encryption and decryption. Clients saves the cpu resources required to encrypt, decrypt data
2. SSE - S3 (AES 256) - AWS manages both the encryption process and the keys. S3 creates a Root Key which will be used to encrypt/decrypt all the objects. this Root key cannot be access by customers and are rotated internally out of your visibility and control. There are some limitations like, If you are in a regulatory environment where the keys and access to the keys need to be controlled then this is not suitable. You cannot channge the key rotation policy and cannot implement role seperation, that is some body who has FullS3Admin access can also read or write data.
3. SSE-KMS - This fixes all limitations introduced by SSE-S3 by using a KMS Key for encryption instead of the S3 managed Root Key. You can choose to use a customer managed KMS. That means you can manage the key material, access and rotation. It also provides auditing and logging of the KMS Key usage via CloudTrail. SSE-KMS gives you Role Seperation.

`Bucket Default Encryption` - SSE - S3 (AES 256) is the bucket default encryption mode configured at the bucket level and comes into play when `x-amz-server-side-encryption` header is not set. Allowed values for the header are AES256 or aws:kms.

`S3 Object - Storage Classes`

**S3 Standard**
1. Onjects are replicated across at least 3 AZs in the AWS Region.
2. 99.999999999 (eleven 9s) durability for 10,000,000 objects and 1 object loss oer 10,000 years.
3. Replication over 3 AZs and content MD5 checksums are used to delect and fix any data corruption.
4. When objects are stored, S3 API responds with a HTTP/1.1 200 OK,
5. Billing - $ per GB per month for data stored, $ per GB for data transfer out (in is free) and $ per 1000 api requests. No specific retrieval fee, no minimum duration, no minimum size.
6. S3 Standard has a milliseconds first byte latency and objects can be made publicly available.
7. S3 Standard must be used for frequently accessed data which is important and non replacable.

**S3 Standard - IA**
1. Offers the same replication, durability, CRC's as S3 Standard for half the price of S3 Standard with additional Per GB data retrieval fee and has a minimum duration charge of 3 days and minimum capacity charge of 128 KB per Object.
2. S3 Standard IA should be used for long lived and larger objects which are important but where access or reteieval is InFrequent.

**S3 One Zone IA**
1. Cheaper than S3 Standard and S3 Standard IA. Has the same per GB data retrieval fee, minimum duration charge of 3 days and minimum capacity charge of 128 kb per object like S3 Standard IA but does not provide the multi az resilience model instead only one az is used within the region.
2. 99.999999999 (eleven 9s) durability unless the az fails.
3. S3 One Zone IA should be used for long lived data which is Non-Critical / Replacable and where access is InFrequent. Ex: cross region replicated data for backups.

**S3 Glacier - Instant**
1. LIke S3 Standard IA but cheaper storage, more expensive retrievals and longer minimum storage.
2. 99.999999999% (eleven 9s) durability, 3 AZ Replication, Content MD5 Checksums, CRC.
3. Billing - Per GB Retrieval Fee, Minimum duration charge of 90 Days, Minimum capacity charge of 128 KB per Object.
4. S3 Glacier Instant should be used for long-lived data accessed once per quarter with millisecond access.

**S3 Glacier - Flexible**
1. Super cheap with trade-offs and used to store cold objects.
2. Offers the same eleven 9s durability and multi az replication.
3. Objects cannot be made publicly accessible. Any access of data beyond the metadata requires a retrieval process. Data in Glacier - Flexible is retrieved to S3 Standard IA temporarily.
4. Retrieval Types - Expedited (1 to 5 mins), Standard (3 to 5 hours), Bulk (5 to 12 hours). So, Faster the retrieval process the more it gets expensive.
5. First byte latency is in Minutes or Hours.
6. 40 KB Min Size and 90 Days Min Duration.
7. S3 Glacier Flexible is suitable to store archival data where frequent or realtime access in not needed for yers with minutes to hours retrieval time.

**S3 Glacier - Deep Archive**
1. Much cheaper than S3 Glacier Flexible but with more restrictions - 40 KB Min Size, 180 Day Min Duration, Objects cannot be made plulicly accessible and access of data requires a retrieval process, Objects are retrieved to S3 Standard IA teporarily.
2. Retrieval Types - Standard (12 Hours) and Bulk (up to 48 Hours). So First byte Latency could be Hours or Days.
3. S3 Glacier Deep Archive class is suitable to store archical data that rarely if ever needs to be accessed and tolerated hours or days for retrieval.

**S3 Intelligent - Tiering**
1. Data Tiers - Frequent Access, InFrequent Access, Archive Instant Access, Archive Access, Deep Archive.
2. Intelligent Tiering monitors and automatically moves any object not access for 30 dats to a low cost infrequent access tier and eventually to archive instant access or deep archive tiers based on the Intelligent - Tiering archive configurations set on the buckets.
3. Has a monitoring and automation cost per 1000 objects. Cost of the tiers are the same as their s3 base classes.

`S3 LifeCycle Rules Configuration`
1. A lifecycle configuration is a set of rules that consists of sctions on a bucket or group of objects and it is used for cost optimization.
2. Action Types,
    1. Transition Actions
    2. Expiration Actions
3. Transition Flow: S3 Standard -> S3 Standard IA -> S3 Intellegent Tiering -> S3 One Zone IA -> S3 Glacier Instant  -> S3 Glacier Flexible  -> S3 Glacier Deep Archive.
4. An object can be configured to transition from a top level class to any of the lower level class with one limitation as from S3 One Zone IA object cannot move to S3 Glacier Instant.
5. Smaller objects can cost more while transitioning to S3 Standard IA or S3 Intellegent Tiering or S3 One Zone IA from S3 Standard. Also not that a minimum of 30 days is required before transition.

`S3 Replication`
1. Cross-Region Replication or Same-Region Replication. 
2. In both cases, 
    1. The buckets can be in the same accounts or different accounts.
    2. Replication configuration is applied to the source bucket.
    3. IAM Role is used for replication configuration. The Role is allowed to trust the S3 Service and the roles permission policy allows access to the role to read from the source bucket and write to the destination bucket.
    4. Replication is Encrypted - SSL
3. For cross account replication, we must add a bucket policy on the destination bucket to allow an IAM Roles in the source bucket account to write or replicate objects in the destination bucket.
4. Replication options,
    1. All objects or a subset.
    2. Storage class on the destination bucket. Default is to maintain the same as the source.
    3. Ownership of the objects in the destination buckets. Default is the maintain the same account owner as the source.
    4. Replcation Time Control (RTC) - 15 mins SLA.
5. Replication Considerations,
    1. Not retroactive.
    2. Versioning need to be ON to enable replication.
    3. One way replication.
    4. not capable to replicate SSE-C Objects.
    5. Source bucket owner needs permissions to the objects.
    6. Cannot replicate bucket configurations or system events like an object moved to another class due to a lifecycle rule.
    7. Cannot replicate Glacier or Glacier Deep Archive classes.
    8. DELETES are not replicated by default, but you can optionally enable it.
6. Why use replication ?
    1. SRR - Log Aggregation, Prod and Test Sync, Resilience with strict soverignity.
    2. CRR - Global Resilience Improvements, Latency Reduction.

`Pre Signed URLs`
1. A way to give another person or application access to objects inside of an S3 Buckets using your credentials in a safe and secure process.
2. Granting an unauthenticated user access to an S3 bucket by making the bucket public, providing them with a permanent AWS Identity, or handing out temporary AWS credentials are not ideal solutions. Instead, the ideal solution is to use pre-signed URLs, which grant time-limited, secure access to specific objects without exposing the rest of the bucket.
3. Pre Signed URL's allows an AWS Identity to generate a URL with access permissions encoded into it for a specific bucket and object, valid for a certain period of time.
4. Pre-Signed URLs can be used for both Download (GET) and Upload (PUT).
5. You can create a URL for a given objects that you have no access to, however such urls will also dont have access to the object since you dont have access - When using the pre-signed url, the permissions match the Identity which generated it.
6. Access denied when using a pre-signed url could mean that the generation id never had the access or it does not have access now.

`S3 Select & Glacier Select`
When application retrieves larger s3 object (5 TB), it takes time and uses a lot of disk space. Filtering the data at the client side is not helpful because you have already downloaded it before filtering can be applied. The solution for this problem is S3 Select or Glacier Select - It offers you to Select Part of the Object using SQL Like Statements (Per Filtered by S3).
1. Allowed to operate on CSV / JSON objects.
2. Reduces usage cost by cutting down on the object retrieval cost.
3. Up to 400% Faster and 80% Cheaper.

`S3 Events`
1. Event Notification by S3 - Notifications are generated when events occur in a bucket and it can be delivered to SNS, SQS & Lambda Functions. Note: Event destinations like SNS, SQS, Lambdas must have attached resource policy to allow s3 to send notifications.
2. Event Types,
    1. Object CREATE - Put, Post, Copy, MultiPart Upload.
    2. Object DELETE - Delete, Delete Marker.
    3. Object RESTORE - Initiated, Completed
    4. Replication - Operation Missed threshold, Operation Replicated after threshold, Operation failed replication and more.
3. `Event Bridge` is a newer and much better alternative to S3 events as it supports more types of events and more services.

`S3 Access Logs`
1. Stores bucket and object access logs for a source bucket as a Log File in a target bucket.
2. Log files consists of log records. The records are newline delimited and the record attributes are space delimited.
3. Access Logging can be enabled via the console ui or via bucket logging api.

`S3 Object Lock`
1. Prevents accidental deletion of critical Object version. Object locks are enabled on New Buckets. For existing buckets, contact aws support.
2. Write Once Read Many (WORM) - No Delete / No Overwrite.
3. Required Versioning and individual versions are locked.
4. Object versions has a Retention Period and Legal Hold. Each version can have both retention period and legan hold or either one or none.
5. S3 Object Lock - Retention
    1. Retention period is specified in days and years.
    2. Retention Modes,
        1. Compliance Mode - Retention setting cant be adjusted, deleted or overwritten. Even the Root User cant change until retention expires.
        2. Governance Mode - Special permissions can be granted allowing lock settings to be adjusted. Requires S3:BypassGovernanceRetention permission and x-amz-bypass-gonernance-retention: true header set. By default this header is set while operating in the aws console ui.
6. S3 Object Lock - Legal Hold
    1. Set on an object version ON or OFF.
    2. No deletes or changes to the object untill removed.
    3. No Retention Period.
    4. Required S3:PutObjectLegalHold permission to add or remove legal hold.
